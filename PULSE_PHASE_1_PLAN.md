# Pulse — Phase 1: Functional MVP

## 1. Objective

Build a functional full-stack infrastructure monitoring platform called **Pulse**.

The Phase 1 MVP should allow a user to:

1. Register a service for monitoring.
2. View registered services.
3. Generate simulated CPU and memory metrics.
4. Store metrics in PostgreSQL.
5. Display metrics on a React dashboard.
6. Receive metric updates in real time using WebSockets.
7. Define basic CPU threshold alerts.
8. Generate and store alerts when thresholds are exceeded.
9. View recent alerts on the dashboard.
10. Run the entire application using Docker Compose.

The goal of Phase 1 is to establish a complete working vertical slice before adding advanced distributed-system features.

# 4. Core Domain Entities

## 4.1 Service

Represents an application or service being monitored.

Fields:

* id
* name
* description
* endpoint
* status
* createdAt

Example:

```text
Payment API
https://api.example.com
Status: UP
```

---

## 4.2 Metric

Represents a system measurement associated with a service.

Fields:

* id
* serviceId
* cpuUsage
* memoryUsage
* timestamp

Example:

```text
CPU: 63.2%
Memory: 71.4%
Timestamp: 21:42:13
```

Metrics will initially be generated by a backend simulator.

---

## 4.3 Alert

Represents a threshold violation.

Fields:

* id
* serviceId
* type
* message
* severity
* timestamp
* resolved

Example:

```text
HIGH CPU
Payment API exceeded 80% CPU
Severity: WARNING
```

# 5. Backend Requirements

## 5.1 Service Management

Implement REST endpoints for:

```text
POST   /api/services
GET    /api/services
GET    /api/services/{id}
DELETE /api/services/{id}
```

The backend must validate incoming service data and return appropriate HTTP status codes.

---

## 5.2 Metrics

Implement:

```text
GET /api/services/{id}/metrics
```

The backend should periodically generate simulated CPU and memory metrics for registered services.

The metric simulator should:

* Run periodically.
* Generate realistic varying values.
* Associate metrics with the correct service.
* Persist metrics in PostgreSQL.
* Make new metrics available to the frontend in real time.

---

# 6. Real-Time Communication

Use **Spring WebSocket**.

When a new metric is generated:

```text
Metric generated
      ↓
Spring Boot
      ↓
Persist metric
      ↓
WebSocket event
      ↓
React dashboard
      ↓
Charts update automatically
```

The user should not need to refresh the page to see new metrics.

---

# 7. Alert System

Implement basic threshold-based alerting.

Initial rule:

```text
CPU > 80%
      ↓
Generate Alert
      ↓
Persist Alert
      ↓
Send WebSocket notification
      ↓
Display alert on dashboard
```

Implement:

```text
GET /api/services/{id}/alerts
```

The alert system should avoid generating excessive duplicate alerts for every metric update.

# 10. Database

Use PostgreSQL.

Initial tables:

```text
services
metrics
alerts
```

Relationships:

```text
Service
   │
   ├──── Metrics
   │
   └──── Alerts
```

Use JPA/Hibernate for persistence.

Database configuration should be supplied through environment variables rather than hard-coded credentials.

# 17. Phase 1 Definition of Done

Phase 1 is complete only when the following workflow works successfully:

1. Start the application using Docker Compose.
2. Open the React dashboard.
3. Register a service.
4. Service appears in the dashboard.
5. Backend begins generating simulated metrics.
6. Metrics are stored in PostgreSQL.
7. CPU and memory charts display the metrics.
8. Charts update automatically through WebSockets.
9. CPU exceeds the configured threshold.
10. An alert is generated.
11. The alert is stored in PostgreSQL.
12. The alert appears on the dashboard without refreshing.
13. Existing data remains available after refreshing the browser.
14. Backend tests pass.
15. Frontend builds successfully.
16. Docker Compose starts all required services successfully.
17. README contains complete setup and usage instructions.
